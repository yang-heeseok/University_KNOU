# 빅데이터의이해와활용 — 2026학년도 2학기 중간과제 1번

작성일: 2026-10-12  
문항: 웹 스크래핑과 오픈 API에 관한 생성형 인공지능 답변의 오류 지적 및 교정

## 1. 지문의 잘못된 부분과 교정

### 가. 웹 스크래핑이 매우 안정적이고 반영구적이라는 설명

웹 스크래핑은 웹페이지에서 필요한 정보를 추출하는 방식이다. 대표적으로 HTML 구조를 분석하고 CSS 선택자나 XPath 등을 이용하여 특정 항목을 가져온다. 크롤링은 링크를 따라 여러 페이지를 탐색하고 수집하는 과정에, 스크래핑은 수집한 페이지에서 필요한 데이터를 추출하는 과정에 초점이 있다. 두 과정은 함께 사용되지만 엄밀하게는 동일한 개념이 아니다. [Scrapy 공식 문서](https://docs.scrapy.org/en/latest/intro/overview.html)

페이지의 태그, 속성, 배치가 바뀌면 기존 추출 규칙이 맞지 않아 누락이나 오류가 발생할 수 있다. 동적으로 표시되는 내용, 로그인 요구, 접근 제한 등도 수집에 영향을 준다. 따라서 웹 스크래핑을 반영구적인 방식으로 보는 것은 잘못이며, 구조 변경 감지와 추출 결과 검증 등 지속적인 유지보수가 필요하다.

### 나. 법적·윤리적 문제가 전혀 없다는 설명

인터넷에서 열람할 수 있다는 사실이 무제한 수집과 재이용을 허락한다는 의미는 아니다. 수집 대상과 이용 방법에 따라 저작권, 데이터베이스제작자의 권리, 개인정보, 사이트 이용약관 등을 검토해야 한다. 저작권법은 데이터베이스의 전부 또는 상당한 부분에 관한 제작자의 권리를 규정하며, 작은 부분이라도 반복적·체계적으로 이용하는 경우 문제가 될 수 있다. 따라서 모든 스크래핑이 불법이라고 할 수도 없지만, 아무 문제가 없다고 단정하는 것도 부정확하다. [국가법령정보센터, 저작권법 제93조](https://www.law.go.kr/법령/저작권법/제93조)

실무적으로는 요청 간격과 동시 접속 수를 조절하여 서버에 과도한 부담을 주지 않아야 한다. 또한 robots.txt에 표시된 크롤러 접근 규칙을 확인해야 한다. 다만 robots.txt는 접근 권한이나 콘텐츠 이용허락 자체를 부여하는 장치가 아니므로, 이 규칙만으로 수집·재이용의 적법성을 판단할 수는 없다. [Scrapy 공식 문서](https://docs.scrapy.org/en/latest/intro/overview.html), [IETF, RFC 9309 §1](https://www.rfc-editor.org/rfc/rfc9309.html#section-1)

### 다. 오픈 API는 실시간 데이터를 제공할 수 없다는 설명

오픈 API는 제공자가 외부 이용을 위해 공개한 인터페이스이다. 이용자는 정해진 주소와 요청 항목으로 데이터를 요청하고, JSON이나 XML 등 약속된 형식으로 응답을 받는다. 실시간 제공 여부는 API라는 방식 때문에 결정되는 것이 아니라 원천 데이터의 갱신 주기와 제공 시스템의 운영 방식에 달려 있다. 실제로 서울특별시의 버스위치정보조회 API는 버스의 실시간 위치 정보를 제공한다. [서울 열린데이터광장 이용안내](https://data.seoul.go.kr/together/guide/useGuide.do), [공공데이터포털, 서울특별시 버스위치정보조회 서비스](https://www.data.go.kr/data/15000332/openapi.do)

따라서 API를 통해 실시간 또는 실시간에 가까운 서비스를 구현할 수 있다. 다만 원천 정보가 반영되는 데 걸리는 시간이나 통신 지연 때문에 실제 현장과 완전히 일치하는 무지연 정보가 항상 보장되는 것은 아니다.

### 라. 행정 절차가 복잡하여 공공기관 활용 사례를 찾기 어렵다는 설명

오픈 API의 이용 조건은 서비스마다 다르다. 회원가입, 활용 신청, 인증키 발급이 필요한 경우가 있지만 이를 일률적으로 복잡하다고 단정할 수는 없다. 서울 열린데이터광장과 서울시 교통정보시스템 등은 공공데이터를 오픈 API로 제공하고 있다. 따라서 공공기관에서 활용 사례를 찾기 어렵다는 주장은 사실과 다르다. [서울 열린데이터광장 이용안내](https://data.seoul.go.kr/together/guide/useGuide.do), [서울시 TOPIS OPEN API 안내](https://topis.seoul.go.kr/refRoom/openRefRoom_4.do)

API를 이용하면 웹페이지의 화면 구조 대신 정해진 데이터 항목을 처리할 수 있어 수집과 후처리를 체계화하기 쉽다. 그러나 API도 호출량 제한, 제공 항목 변경, 서비스 종료 등에 영향을 받을 수 있으므로 항상 안정적이거나 무제한으로 이용할 수 있다고 보아서는 안 된다. 예를 들어 서울교통 빅데이터플랫폼은 API 활용 신청 절차와 일일 호출량 제한을 안내한다. [서울교통 빅데이터플랫폼 Open API 이용안내](https://t-data.seoul.go.kr/userguide/guideopenapi.do)

### 마. 2009년 서울버스와 2020년 공공마스크 앱을 같은 사례로 묶은 설명

두 사례는 시기와 데이터 제공 방식을 구분해야 한다. 2009년 서울버스는 공공데이터 개방 제도가 충분히 정비되기 전에 웹에 공개된 버스정보를 활용한 초기 사례이다. 개발자 유주완은 직접 작성한 글에서 각 지역 버스정보사이트와 앱을 연결했다고 설명했으며, 특정 지역의 정보 접근이 차단되었다가 이용자들의 항의 이후 해제된 경험도 소개했다. 이는 공공정보의 민간 활용 수요와 안정적인 개방 체계의 필요성을 보여준다. 초기 서울버스를 처음부터 현재와 같은 공식 오픈 API 기반 서비스였다고 단정하여 교정하는 것 역시 피해야 한다. [유주완, 「혁신의 첫 걸음, 공공정보 개방」, 2013-09-09](https://gonggam.korea.kr/newsContentView.es?b_list=9&code_cd=&content=NC002&mid=a12503000000&nPage=778&news_id=EBC6D401386A4203E0540021F662AC5F&section_id=NCCD_POLICY)

반면 2020년 공공마스크 앱은 정부가 개방한 판매정보 API를 민간이 활용한 대표적인 사례이다. 정부는 2020년 3월 10일 공적 마스크 판매 데이터를 공개하면서, 건강보험심사평가원이 제공한 데이터를 한국정보화진흥원이 가공하고 네이버 클라우드를 통해 오픈 API로 제공한다고 밝혔다. 민간 개발자들은 이를 이용해 판매처와 재고 정보를 알려주는 웹·앱 서비스를 개발할 수 있었다. 따라서 마스크 앱까지 서울시 버스정보 사이트를 스크래핑하여 만들었다는 지문의 설명은 데이터의 대상과 수집 경로를 모두 혼동한 것이다. [과학기술정보통신부, 「“마스크 있는 곳, 앱으로 확인하세요”…마스크 판매정보 공개」, 2020-03-10](https://www.korea.kr/news/policyNewsView.do?newsId=148870119)

법률의 시점도 틀렸다. 「공공데이터의 제공 및 이용 활성화에 관한 법률」은 2013년 7월 30일 공포되어 같은 해 10월 31일 시행되었다. 2009년은 이 법의 시행 전이지만, 2020년은 시행 이후이다. 또한 해당 법이 없었다는 사실만으로 데이터를 제공하거나 API를 운영하는 것이 기술적으로 불가능했다고 추론할 수도 없다. [안전행정부, 시행령 제정안 입법예고](https://www.mois.go.kr/frt/bbs/type001/commonSelectBoardArticle.do?bbsId=BBSMSTR_000000000017&nttId=18842), [안전행정부, 「공공데이터 족쇄 풀어 일자리 만든다!」, 2013-10-30](https://mois.go.kr/frt/bbs/type010/commonSelectBoardArticle.do?bbsId=BBSMSTR_000000000008&nttId=30053)

## 2. 지문을 교정하여 다시 작성한 답변

웹 스크래핑과 오픈 API는 인터넷상의 데이터를 수집하는 데 활용할 수 있지만, 데이터에 접근하고 처리하는 방식이 다르다. 웹 스크래핑은 웹페이지의 HTML 등을 분석하여 필요한 정보를 추출하는 방식이다. 별도의 API가 없는 웹페이지에도 적용할 수 있지만, 페이지 구조 변경이나 접근 제한에 따라 수집 프로그램이 작동하지 않을 수 있어 유지보수가 필요하다. 또한 공개된 정보라도 저작권, 데이터베이스제작자의 권리, 개인정보 및 이용약관을 검토해야 하며, 과도한 요청으로 서버 운영에 부담을 주지 않아야 한다. [Scrapy 공식 문서](https://docs.scrapy.org/en/latest/intro/overview.html), [저작권법 제93조](https://www.law.go.kr/법령/저작권법/제93조)

오픈 API는 제공자가 정한 규격에 따라 데이터를 요청하고 JSON이나 XML 등의 형식으로 받는 인터페이스이다. 정해진 항목으로 데이터를 받아 자동 처리하기에 편리하며, 원천 데이터와 시스템의 갱신 주기에 따라 실시간 정보도 제공할 수 있다. 서울시 버스위치정보조회 API가 그 예이다. 다만 인증키, 호출량 제한, 이용허락 조건과 API 변경 여부 등을 확인해야 한다. 따라서 실무에서는 필요한 항목과 갱신 주기를 충족하는 공식 API가 있는지 먼저 확인하고, 웹 스크래핑이 필요한 경우에는 이용 조건과 유지보수 비용을 함께 고려하는 것이 합리적이다. [서울 열린데이터광장 이용안내](https://data.seoul.go.kr/together/guide/useGuide.do), [서울특별시 버스위치정보조회 서비스](https://www.data.go.kr/data/15000332/openapi.do), [서울교통 빅데이터플랫폼 이용안내](https://t-data.seoul.go.kr/userguide/guideopenapi.do)

활용 사례도 구분해야 한다. 2009년 서울버스는 웹에 공개된 버스정보를 민간이 활용한 초기 사례로서, 정보 접근 차단 논란을 통해 공공데이터 개방의 필요성을 드러냈다. 반면 2020년 공공마스크 앱은 공적 마스크 판매정보를 오픈 API로 개방하고 민간이 이를 활용하여 서비스를 만든 사례이다. 공공데이터법은 2013년 10월 31일부터 시행되었으므로 두 사례를 모두 법률 제정 이전의 스크래핑 사례로 묶는 것은 잘못이다. 두 사례의 차이는 공공정보를 웹에서 활용하던 초기 상황과, 정부가 데이터 제공 통로를 마련하여 민간의 서비스 개발을 지원한 상황의 차이를 보여준다. [서울버스 개발자 기고](https://gonggam.korea.kr/newsContentView.es?b_list=9&code_cd=&content=NC002&mid=a12503000000&nPage=778&news_id=EBC6D401386A4203E0540021F662AC5F&section_id=NCCD_POLICY), [공적 마스크 판매정보 공개 발표](https://www.korea.kr/news/policyNewsView.do?newsId=148870119), [공공데이터법 시행 발표](https://mois.go.kr/frt/bbs/type010/commonSelectBoardArticle.do?bbsId=BBSMSTR_000000000008&nttId=30053)
